= Hazelcast Cluster Manager

This is a cluster manager implementation for Vert.x that uses https://hazelcast.com[Hazelcast].

It is the default cluster manager used in the Vert.x CLI, but it can be replaced with another implementation as Vert.x cluster managers are pluggable.

This implementation is packaged inside:

[source,xml,subs="+attributes"]
----
<dependency>
  <groupId>${maven.groupId}</groupId>
  <artifactId>${maven.artifactId}</artifactId>
  <version>${maven.version}</version>
</dependency>
----

In Vert.x a cluster manager is used for various functions including:

* Discovery and group membership of Vert.x nodes in a cluster
* Maintaining cluster wide topic subscriber lists (so we know which nodes are interested in which event bus addresses)
* Distributed Map support
* Distributed Locks
* Distributed Counters

Cluster managers do *not* handle the event bus inter-node transport, this is done directly by Vert.x with TCP connections.

== Using this cluster manager

If you are using Vert.x from the command line, the jar corresponding to this cluster manager (it will be named `${maven.artifactId}-${maven.version}.jar`
should be in the `lib` directory of the Vert.x installation.

If you want clustering with this cluster manager in your Vert.x Maven or Gradle project then just add a dependency to
the artifact: `${maven.groupId}:${maven.artifactId}:${maven.version}` in your project.

If the jar is on your classpath as above then Vert.x will automatically detect this and use it as the cluster manager.
Please make sure you don't have any other cluster managers on your classpath or Vert.x might
choose the wrong one.

You can also specify the cluster manager programmatically if you are embedding Vert.x by specifying it on the options
when you are creating your Vert.x instance, for example:

[source,$lang]
----
{@link examples.Examples#example1()}
----

== Configuring this cluster manager

=== Selecting member or client mode

The default is an embedded Hazelcast member. For automatic cluster-manager discovery, including CLI use,
select the mode with `vertx.hazelcast.mode`:

[source,bash]
----
java -Dvertx.hazelcast.mode=member -jar ... -cluster
java -Dvertx.hazelcast.mode=client -jar ... -cluster
----

The only accepted values are `member` and `client`. A client connects to separately running Hazelcast members;
it does not start a member or store data partitions. Prepare the external members as described under
<<clientmode, Connecting as a Hazelcast client>>.

Applications can explicitly inject `new MemberMode()`, `new MemberMode(config)`, `new MemberMode(existingInstance)`,
`new ClientMode()`, or `new ClientMode(clientConfig)` into `HazelcastClusterManager`.
An explicitly injected mode selects the behavior. If `vertx.hazelcast.mode` is also set, it must agree with that mode.
Mode validation occurs before the manager allocates cluster resources.

=== Configuring with XML

Member and client configurations use separate XML schemas and files:

[cols="1,1,1",options="header"]
|===
|Source |Member mode |Client mode
|Explicit location property |`vertx.hazelcast.config` |`vertx.hazelcast.client.config`
|Classpath override |`cluster.xml` |`client-cluster.xml`
|Packaged file |`default-cluster.xml` |`default-client-cluster.xml` (template)
|XML root |`hazelcast` |`hazelcast-client`
|Java configuration type |`Config` |`ClientConfig`
|===

Configuration precedence within the selected mode is:

. A programmatically supplied configuration object.
. The explicit location system property for that mode.
. The mode's override file at the classpath root.
. The mode's default packaged in the jar.

The packaged member configuration uses multicast. The packaged client configuration is a template with no
connection target and automatic detection disabled. Selecting client mode requires explicitly configured member
addresses or an enabled discovery provider in XML or `ClientConfig`. A cluster name alone is insufficient.
An otherwise unconfigured `new ClientConfig()` is also rejected, even though Hazelcast enables automatic detection
by default. Configure a specific discovery provider instead of relying on that default.
`ConfigUtil.loadClientConfig()` can return the template for customization; attempting to start it without a target
fails with a configuration error before creating a Hazelcast client.

Both location properties accept a filesystem path or a `classpath:` resource:

[source,bash]
----
# Embedded member with external XML
java -Dvertx.hazelcast.config=./config/member.xml -jar ... -cluster

# Client with external XML
java -Dvertx.hazelcast.mode=client -Dvertx.hazelcast.client.config=./config/client.xml -jar ... -cluster

# Client XML packaged as a classpath resource
java -Dvertx.hazelcast.mode=client -Dvertx.hazelcast.client.config=classpath:config/client.xml -jar ... -cluster
----

For automatic classpath overrides, put `cluster.xml` or `client-cluster.xml` at the root of the application jar,
or add the directory containing the file to the launcher classpath, for example `vertx run MyVerticle -cp conf -cluster`.
Files for both modes may coexist on the classpath; only the selected mode's override is read.

An explicitly selected XML file that is missing, unreadable, malformed, or of the wrong configuration type fails
startup with its source location in the error. It does not fall back to a different configuration.
A malformed classpath override also fails instead of falling back to the packaged default.

CAUTION: The plugin does not use Hazelcast's native `hazelcast.config` or `hazelcast.client.config` properties
for configuration loading. Use the `vertx.hazelcast.*` properties above.

=== Incompatible settings

The manager rejects these combinations before starting Hazelcast:

* Unknown `vertx.hazelcast.mode` values or a selector that contradicts the injected mode.
* Both member and client XML location properties being set, or the other mode's property being set.
* Member address properties `hazelcast.local.localAddress` or `hazelcast.local.publicAddress` in client mode.
  Configure the Vert.x event-bus bind and public addresses separately in client mode.
* XML location properties with an externally supplied member instance: configure that instance before passing it in.
* Client mode without member addresses or an enabled discovery provider, including XML that only sets a cluster name.
* Blank member addresses in client configuration.
* Applying member configuration to client mode or replacing an explicitly configured mode through `setClientConfig`.
* Changing configuration after the manager has joined.

An externally supplied member also rejects replacement configuration objects. Reapplying its existing configuration
object has no effect on the already running member.

=== Discovery options

Hazelcast supports several discovery options.
The default configuration uses multicast, so you must have multicast enabled on your network for this to work.

For full documentation on how to configure discovery differently please consult the Hazelcast documentation.

=== Changing local and public address with system properties

Sometimes, cluster nodes must bind to an address that is not reachable by other members.
For example, this may happen when nodes are not in the same network area, or on certain clouds with specific firewall configurations.

The bind address and public address (the address advertised to other members) can be set with system properties:

[source,bash]
----
-Dhazelcast.local.localAddress=172.16.5.131 -Dhazelcast.local.publicAddress=104.198.78.81
----

You can pass an already running Hazelcast member `HazelcastInstance` in the same JVM to the cluster manager.
This constructor expects a member, even though Hazelcast clients also implement `HazelcastInstance`:

[source,$lang]
----
{@link examples.Examples#example3(com.hazelcast.core.HazelcastInstance)}
----

In this case, Vert.x is not the cluster owner and so do not shutdown the cluster on close.

Notice that the custom Hazelcast instance need to be configured with:

[#_minimal_required_hazelcast_configuration]
[source,xml]
.Minimal required Hazelcast configuration
----
<member-attributes>
  <attribute name="__vertx.nodeId">unique-identifier</attribute>
</member-attributes>

<multimap name="__vertx.subs">
  <backup-count>1</backup-count>
  <value-collection-type>SET</value-collection-type>
</multimap>

<map name="__vertx.haInfo">
  <backup-count>1</backup-count>
</map>

<map name="__vertx.nodeInfo">
  <backup-count>1</backup-count>
</map>
----

CAUTION: The `__vertx.nodeId` is used by Vert.x as identifier of the node in the cluster.
Make sure to configure unique values across members.

== Connecting as a Hazelcast client

By default, each Vert.x node starts an embedded Hazelcast member. To connect Vert.x to a separately managed
Hazelcast cluster instead, configure a `ClientConfig` before creating the Vert.x instance:

[source,$lang]
----
{@link examples.Examples#clientMode()}
----

The mode owns the Hazelcast lifecycle. Inject `new MemberMode(config)` for an owned embedded member,
`new MemberMode(existingInstance)` for an externally owned member, or `new ClientMode(clientConfig)` for an owned client.
Closing Vert.x stops owned instances; an externally supplied member stays running.

=== Local development example

For development with an already running member on the same host, save this explicit configuration as `client-dev.xml`:

[source,xml]
----
<hazelcast-client xmlns="http://www.hazelcast.com/schema/client-config">
  <cluster-name>dev</cluster-name>
  <network>
    <cluster-members>
      <address>127.0.0.1:5701</address>
    </cluster-members>
  </network>
</hazelcast-client>
----

[source,bash]
----
java -Dvertx.hazelcast.mode=client -Dvertx.hazelcast.client.config=client-dev.xml -jar ... -cluster
----

This deliberately selects the local `dev` cluster. Supply deployment-specific addresses or discovery configuration
for a deployed application. The plugin never starts a server when selecting client mode.

=== Client startup requirements

Client mode requires an existing Hazelcast member cluster. The client does not store data partitions or act as a
Hazelcast member; it connects to the cluster over the network. Vert.x node membership is tracked in the shared
`__vertx.nodeInfo` map, so all participating Vert.x nodes must use this cluster manager version and the cluster
must permit dynamic configuration updates. Before requesting internal distributed objects, client mode installs
`__vertx.haInfo`, `__vertx.nodeInfo`, and `__vertx.clusterInfo` map configurations with one backup, and the `__vertx.subs` multimap configuration
with one backup and `SET` values, matching the packaged member defaults. These objects are created lazily when used.
The configuration updates must be permitted by the cluster's security settings. If existing configurations conflict
or an update is rejected, client startup fails and its owned client is shut down.

A failed `join()` rolls back allocated executors, listeners, and registrations, and shuts down any Hazelcast
instance owned by the manager. Externally supplied members remain running. The original startup error is preserved;
cleanup failures are attached as suppressed exceptions. Calling `leave()` after a failed join is safe, and the
same manager can retry joining after the cause of the failure is resolved.

==== Client crash detection

A client process can disappear without running shutdown hooks, for example after `SIGKILL`, Kubernetes `OOMKill`,
or loss of a node. Clean shutdown alone cannot detect these failures: without a liveness lease, the dead node
remains in discovery, its event-bus subscriptions remain eligible for routing, and HA receives no departure event.

Client registrations in `__vertx.nodeInfo` therefore have a renewable TTL. The default TTL is 60 seconds and
clients refresh it every 10 seconds using `setTtl`, which does not recreate a missing or expired entry.
Renewals run on a dedicated thread, separate from both the Vert.x worker pool and the lease watchdog.
Application worker-pool saturation therefore does not delay renewals, and a blocked renewal does not stop the watchdog.
Registration updates, including those triggered by a peer departure, atomically preserve the existing expiry.
A surviving Vert.x node handles expiration as a departure: it removes the dead node's subscriptions, calls
`registrationsLost` and `nodeLeft`, and allows Vert.x HA to fail over eligible deployments and clean up their
`__vertx.haInfo` records. HA still requires a surviving eligible node and its configured quorum. Detection is
not immediate: allow the lease TTL and Hazelcast's expiration-event delivery delay.

Configure the following properties in the injected `ClientConfig`, client XML `<properties>`, or JVM system properties:

[cols="3,1,3",options="header"]
|===
|Property |Default |Meaning
|`vertx.hazelcast.client.lease.ttl.seconds` |60 |Lifetime of an unrenewed client registration.
|`vertx.hazelcast.client.heartbeat.interval.seconds` |10 |Renewal interval; must be positive and at most one third of the TTL.
|===

Choose a TTL that exceeds expected GC pauses and network interruptions. A separate watchdog tracks acknowledged
renewals even while a Hazelcast call is blocked. If renewal cannot be confirmed before the local safety deadline
(one heartbeat interval before the TTL), or the entry has expired, the client becomes unhealthy and stops renewal
and recovery. The default lease-loss action closes Vert.x, including its HTTP servers, but does not exit the JVM.
It does not republish the expired registration. Restart the node to obtain a new identity.

Applications can replace that action with `HazelcastClusterManager.setClientLeaseLossHandler` before joining.
For example, close Vert.x and exit with a nonzero status so a process supervisor can restart the application:

[source,java]
----
{@link examples.Examples#clientLeaseLoss(io.vertx.spi.cluster.hazelcast.HazelcastClusterManager)}
----

The handler receives the affected Vert.x instance and runs once per lost lease on the detecting thread, which
can be the watchdog thread. It must initiate shutdown without blocking and takes responsibility for stopping
the application's clustered workload. A throwing handler falls back to closing Vert.x. A custom action does
not extend the safety deadline or allow the expired identity to rejoin; it controls how the application
responds to fencing.

Clean shutdown cancels renewal and removes the registration immediately. Member-mode registrations do not use
this client lease; member departures continue to use Hazelcast membership events. Both member-mode and client-mode
Vert.x nodes listen for those events, so a crashed member's registration is removed even when only client-mode
Vert.x nodes survive. Members without a Vert.x node attribute are data-only members and do not announce Vert.x departures.

==== Reconnecting after an external-cluster restart

Clients handle both `CLIENT_CONNECTED` and `CLIENT_CHANGED_CLUSTER`. After reconnecting, they reinstall the internal
map configurations and restore their node registration, locally owned subscriptions, and live HA deployment descriptions.
Registration caches are invalidated and membership is reconciled. The existing Vert.x instances, node IDs, event-bus
listeners, and running deployments are retained; applications do not need to restart Vert.x after a short cluster restart.

The `__vertx.clusterInfo` map holds a shared, non-expiring state-generation marker. If the external cluster loses its
internal state, clients establish a new generation and publish fresh leases. A reconnect to the same generation requires
the previous lease to remain valid: an expired or removed lease is never resurrected. Lease-renewal responses belonging
to an earlier connection are ignored. Do not delete this marker independently of the other internal cluster state.

Readiness remains false until recovery completes. Reconnection and recovery must finish before the existing lease safety
deadline; an outage exceeding that deadline invokes the lease-loss action to preserve fencing. Set the lease TTL to cover the
outage duration you intend to tolerate, including planned external-cluster maintenance.

This recovers the surviving processes' Vert.x metadata, not application map contents, counters, or lock state. Use Hazelcast
persistence or application-level recovery if those data must survive a full external-cluster restart. HA descriptions
belonging to processes that also died cannot be reconstructed from their lost in-memory state.

==== Preparing the Hazelcast member classpath

The external members need `vertx-hazelcast` and its runtime dependencies at the same version as the application.
Map configuration alone is insufficient. Shared counters submit entry processors whose implementation is in
`HazelcastCounter`; the partition owner must be able to load that class and its dependencies. The internal node
and subscription maps also contain Vert.x serialization classes. Install these libraries on *every* member before
starting the cluster, including members added later.

For a standalone member, save this as `pom.xml` in a separate directory:

[source,xml,subs="+attributes"]
----
<project xmlns="http://maven.apache.org/POM/4.0.0">
  <modelVersion>4.0.0</modelVersion>
  <groupId>example</groupId>
  <artifactId>vertx-hazelcast-member</artifactId>
  <version>1.0</version>
  <dependencies>
    <dependency>
      <groupId>${maven.groupId}</groupId>
      <artifactId>${maven.artifactId}</artifactId>
      <version>${maven.version}</version>
    </dependency>
  </dependencies>
</project>
----

Copy all runtime dependencies and start the member with that directory on its classpath:

[source,bash]
----
mvn dependency:copy-dependencies -DincludeScope=runtime -DoutputDirectory=member-lib
java -Dhazelcast.config=cluster.xml -cp 'member-lib/*' com.hazelcast.core.server.HazelcastMemberStarter
----

Here `cluster.xml` is the member configuration, including the maps and multimap described above and the cluster
name used by the client. The `hazelcast.config` property in this command configures the standalone Hazelcast
process. For container or service deployments, add the same runtime jars to the member process classpath.

=== Client readiness

The provided cluster health check uses partition safety in member mode. In client mode it performs a remote read
of this Vert.x node's registry entry to confirm connectivity and registration. This client check does not assert
partition safety. Disconnected or recovering clients report down immediately. Registry reads have a one-second
timeout and report down if it expires; other remote-operation errors fail the health-check procedure.

Use client mode when you want to scale the application independently from Hazelcast, isolate application failures
from the data members, or keep application instances from owning data partitions. Embedded members usually provide
lower latency because local operations avoid a client network round trip, and they are simpler when you want each
Vert.x process to join and contribute capacity to the Hazelcast cluster.

IMPORTANT: Make sure Hazelcast is started before and shut down after Vert.x.
Also, the Hazelcast shutdown hook should be disabled (see xml example, or via system property).

== Changing timeout for failed nodes

By default, a node will be removed from the cluster if Hazelcast didn't receive a heartbeat for 60 seconds.
To change this value `hazelcast.max.no.heartbeat.seconds` system property such as in:

[source,bash]
----
-Dhazelcast.max.no.heartbeat.seconds=5
----

Afterwards a node will be removed from the cluster after 5 seconds without a heartbeat.

See https://docs.hazelcast.com/hazelcast/5.3/system-properties[Hazelcast system-properties].

== Troubleshooting clustering

If the default multicast configuration is not working here are some common causes:

=== Multicast not enabled on the machine.

It is quite common in particular on OSX machines for multicast to be disabled by default.Please google for
information on how to enable this.

=== Using wrong network interface

If you have more than one network interface on your machine (and this can also be the case if you are running
VPN software on your machine), then Hazelcast may be using the wrong one.

To tell Hazelcast to use a specific interface you can provide the IP address of the interface in the `interfaces`
element of the configuration. Make sure you set the `enabled` attribute to `true`. For example:

[source,xml]
----
<interfaces enabled="true">
  <interface>192.168.1.20</interface>
</interfaces>
----

=== Using a VPN

This is a variation of the above case. VPN software often works by creating a virtual network interface which often
doesn't support multicast. If you have a VPN running and you do not specify the correct interface to use in both the
hazelcast configuration and to Vert.x then the VPN interface may be chosen instead of the correct interface.

So, if you have a VPN running you may have to configure both the Hazelcast and Vert.x to use the correct interface as
described in the previous section.

=== When multicast is not available

In some cases you may not be able to use multicast as it might not be available in your environment. In that case
you should configure another transport, e.g. TCP  to use TCP sockets, or AWS when running on Amazon EC2.

For more information on available Hazelcast transports and how to configure them please consult the Hazelcast
documentation.

=== Enabling logging

When trouble-shooting clustering issues with Hazelcast it's often useful to get some logging output from Hazelcast
to see if it's forming a cluster properly. You can do this (when using the default JUL logging) by adding a file
called `vertx-default-jul-logging.properties` on your classpath. This is a standard java.util.logging (JUL)
configuration file. Inside it set:

[source,properties]
----
com.hazelcast.level=INFO
----

and also

[source,properties]
----
java.util.logging.ConsoleHandler.level=INFO
java.util.logging.FileHandler.level=INFO
----

== Hazelcast logging

The logging backend used by Hazelcast is `jdk` by default (understand JUL). If you want to redirect the logging to
another library, you need to set the `hazelcast.logging.type` system property such as in:

[source,properties]
----
-Dhazelcast.logging.type=slf4j
----

See the https://docs.hazelcast.com/hazelcast/5.3/clusters/logging-configuration[hazelcast documentation] for more details.

== Using a different Hazelcast version

You may want to use a different version of Hazelcast. The default version is `${hazelcast.version}`. To do so, you
need to:

* put the version you want in the application classpath
* if you are running a fat jar, configure your build manager to use the right version

In this later case, you would need in Maven:

[source,xml,subs="+attributes"]
----
<dependency>
  <groupId>com.hazelcast</groupId>
  <artifactId>hazelcast</artifactId>
  <version>ENTER_YOUR_VERSION_HERE</version>
</dependency>
<dependency>
  <groupId>${maven.groupId}</groupId>
  <artifactId>${maven.artifactId}</artifactId>
  <version>${maven.version}</version>
</dependency>
----

Depending on the version, you may need to exclude some transitive dependencies.

On Gradle, you can achieve the same overloading using:

[source,groovy,subs="+attributes"]
----
dependencies {
 compile ("${maven.groupId}:${maven.artifactId}:${maven.version}"){
   exclude group: 'com.hazelcast', module: 'hazelcast'
 }
 compile "com.hazelcast:hazelcast:ENTER_YOUR_VERSION_HERE"
}
----

== Configuring for Kubernetes

The first step is to configure the discovery plugin inside your Hazelcast configuration, by either providing a custom `cluster.xml` file or programmatically, as described in <<configcluster>>.

https://docs.hazelcast.com/hazelcast/5.3/kubernetes/kubernetes-auto-discovery#discovering-members[discovery modes]: _Kubernetes API_ and _DNS Lookup_.
Please refer to the plugin project page for pros and cons of both modes.

In this document, we will use _DNS Lookup_ discovery.
The following properties have to be changed / added:

[source,xml]
----
<hazelcast>
  <network>
    <join>
      <auto-detection enabled="false"/> <!--1-->
      <multicast enabled="false"/> <!--2-->
      <kubernetes enabled="true"> <!--3-->
        <service-dns>MY-SERVICE-DNS-NAME</service-dns> <!--4-->
      </kubernetes>
    </join>
  </network>
</hazelcast>
----
<1> Disable discovery plugin auto-detection
<2> Disable multicast discovery
<3> Activate Kubernetes discovery
<4> Service DNS, usually in the form of `MY-SERVICE-NAME.MY-NAMESPACE.svc.cluster.local` but depends on the Kubernetes distribution

[IMPORTANT]
====
The configuration excerpt above only contains network related settings.
The actual configuration must contain the <<_minimal_required_hazelcast_configuration, minimal required settings>>.
====

The `MY-SERVICE-DNS-NAME` value must be a *headless* Kubernetes service name that will be used by Hazelcast to identify all cluster members.
A headless service can be created with:

[source,yaml]
----
apiVersion: v1
kind: Service
metadata:
  namespace: MY-NAMESPACE
  name: MY-SERVICE-NAME
spec:
  type: ClusterIP
  clusterIP: None
  selector:
    component: MY-SERVICE-NAME # <1>
  ports:
    - name: hazelcast
      port: 5701
      protocol: TCP
----
<1> Cluster members selected by label

Eventually, attach the `component` label to all deployments that should be part of the cluster:

[source,yaml]
----
apiVersion: apps/v1
kind: Deployment
metadata:
  name: MY-DEPLOYMENT-NAME
  namespace: MY-NAMESPACE
spec:
  selector:
    matchLabels:
      component: MY-SERVICE-NAME
  template:
    metadata:
      labels:
        component: MY-SERVICE-NAME
    spec:
      containers:
        - name: app
          image: MY-IMAGE:MY-TAG
----

Further configuration details are available on the https://docs.hazelcast.com/hazelcast/5.3/kubernetes/kubernetes-auto-discovery#discovering-members[Kubernetes Auto Discovery page].

=== Rolling updates

During rolling updates, it is recommended to replace pods one by one.

To do so, we must configure Kubernetes to:

* never start more than one new pod at once
* forbid more than one unavailable pod during the process

[source,yaml]
----
spec:
  strategy:
    type: Rolling
    rollingParams:
      updatePeriodSeconds: 10
      intervalSeconds: 20
      timeoutSeconds: 600
      maxUnavailable: 1 <1>
      maxSurge: 1 <2>
----
<1> the maximum number of pods that can be unavailable during the update process
<2> the maximum number of pods that can be created over the desired number of pods

Also, the pod readiness probe must take the cluster state into account.
Please refer to the <<one-by-one, cluster administration>> section for details on how to implement a readiness probe with link:../../vertx-health-check/$lang/[Vert.x Health Checks].

== Cluster administration

The Hazelcast cluster manager works by turning Vert.x nodes into members of a Hazelcast cluster.
As a consequence, Vert.x cluster manager administration should follow the Hazelcast management guidelines.

First, let's take a step back and introduce data partitioning and split-brain syndrome.

=== Data partitioning

Each Vert.x node holds pieces of the clustering data: eventbus subscriptions, async map entries, clustered counters... etc.

When a member joins or leaves the cluster, Hazelcast migrates data partitions.
In other words, it moves data around to accomodate the new cluster topology.
This process may take some time, depending on the amount of clustered data and number of nodes.

=== Split-brain syndrome

In a perfect world, there would be no network equipment failures.
Reality is, though, that sooner or later your cluster will be divided into smaller groups, unable to see each others.

Hazelcast is capable of merging the nodes back into a single cluster.
But just as with data partition migrations, this process may take some time.
Before the cluster is fully functional again, some eventbus consumers might not be able to get messages.
Or high-availability may not be able to redeploy a failing verticle.

[NOTE]
====
It is difficult (if possible at all) to make a difference between a network partition and:

- long GC pauses (leading to missed heartbeats checks),
- many nodes being killed forcefully, at-once, because you are deploying a new version of your application
====

=== Recommendations

Considering the common clustering issues discussed above, it is recommended to stick to the following good practices.

==== Graceful shutdown

Avoid stopping members forcefully (e.g, `kill -9` a node).

Of course process crashes are inevitable, but a graceful shutdown helps to get the remaining nodes in a stable state faster.

[[one-by-one]]
==== One node after the other

When rolling a new version of your app, scaling-up or down your cluster, add or remove nodes one after the other.

Stopping nodes one by one prevents the cluster from thinking a network partition occured.
Adding them one by one allows for clean, incremental data partition migrations.

The cluster safety can be verified with link:../../vertx-health-check/$lang/[Vert.x Health Checks]:

[source,$lang]
----
{@link examples.Examples#healthCheck(io.vertx.core.Vertx)}
----

After creation, the health check can be exposed over HTTP with a link:../../vertx-web/$lang/[Vert.x Web] router handler:

[source,java]
----
import io.vertx.core.Vertx;
import io.vertx.ext.healthchecks.HealthChecks;
import io.vertx.ext.web.healthchecks.HealthCheckHandler;
import io.vertx.ext.web.Router;

public class ReadinessExample {
  public static Router createRouter(Vertx vertx, HealthChecks checks) {
    Router router = Router.router(vertx);
    router.get("/readiness").handler(HealthCheckHandler.createWithHealthChecks(checks));
    return router;
  }
}

==== Using Lite Members

To minimize the time a Vert.x cluster spends accomodating a new topology, you may use external data nodes and mark Vert.x nodes as https://docs.hazelcast.com/hazelcast/5.3/maintain-cluster/lite-members[_Lite Members_].

_Lite Members_ participate in a Hazelcast cluster like regular members, but they do not own any data partition.
Therefore, Hazelcast does not need to migrate partitions when such members are added or removed.

IMPORTANT: You must start the external data nodes beforehand as Hazelcast won't create a cluster with _Lite Members_ only.

To start an external node, you can use the Hazelcast distribution start script, or proceed programmatically.

Vert.x nodes can be marked as _Lite Members_ in the XML configuration:

[source,xml]
----
<lite-member enabled="true"/>
----

You can also do it programmatically:

[source,$lang]
----
{@link examples.Examples#liteMemberConfig()}
----
